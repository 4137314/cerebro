Threads and monitors in Java

Every Java object has an intrinsic lock and a wait set, i.e. it is a monitor: synchronized methods or blocks acquire the lock (mutual exclusion), wait() releases it and sleeps until notify()=/=notifyAll(), volatile guarantees visibility of single variables; higher-level tools live in java.util.concurrent.

Definition

  • Creating threads: new Thread(runnable).start(), or better an ExecutorService that reuses a pool: pool.submit(() -> work()) returns a Future.
  • synchronized void m() locks this (static synchronized locks the Class object); synchronized (obj) { ... } locks obj. Locks are reentrant: a thread holding a lock can enter other blocks synchronised on it.
  • wait() (only while holding the lock) releases it and suspends the thread; notify() wakes one waiter, notifyAll() all of them; the woken thread re-acquires the lock before returning from wait.
  • volatile fields: every read sees the latest write (no caching in registers), but count++ on a volatile is still a race — use AtomicInteger.
  • java.util.concurrent: ReentrantLock and Condition (C++-like), ConcurrentHashMap, BlockingQueue (ready-made producer–consumer), CountDownLatch, AtomicLong.

Example

Intuition

In Java the lock comes with the object: you do not create mutexes, you decide which object guards which data.

Pitfall

Synchronising on different objects for the same data protects nothing. And calling wait or notify without holding the object's lock throws IllegalMonitorStateException.
