List scheduling

Scheduling with limited resources is NP-hard; list scheduling goes cycle by cycle, keeps the operations whose predecessors are done (ready list) and starts as many as the free units allow, choosing by priority — usually the smallest mobility or the longest path to the sink; a dual version minimises resources under a latency bound.

Method

Resource-constrained (minimise latency with units of type ): in each cycle , for each type

  1. : ready operations of type (all predecessors finished);
  2. : operations of type still executing;
  3. start the operations of with highest priority.

Latency-constrained (minimise units for a bound ): compute ALAP times; in each cycle schedule all ready operations with zero slack (forced), adding units if needed, then the others that fit in the units already allocated.

Example

Solver graph, unit delays, priority = least mobility.

cycle 1 multiplier 1 ALU 2 multipliers 1 ALU
1 v1 v10 v1, v2 v10
2 v2 v11 v3, v4 v11
3 v3 — v5, v6 v7
4 v4 v7 — v8
5 v5 — — v9
6 v6 v8    
7 — v9    

One multiplier: latency 7 (six multiplications in series, then v9). Two multipliers: latency 5, and the single ALU is now the bottleneck (v8 and v9 compete in cycle 4); with two ALUs it drops to the critical-path bound of 4.

Intuition

A greedy foreman: each morning, give the free machines to the most urgent jobs that are ready.

Pitfall

List scheduling is a heuristic: a different priority can give a shorter schedule, and no single priority is best for every graph. It is fast, plus the cycles, which is why it is the workhorse of HLS tools.
