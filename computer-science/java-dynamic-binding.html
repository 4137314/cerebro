The Java method selection rule

For a call x.f(a1,…,an) the compiler fixes the signature, choosing among the methods of the static type of x the most specific one applicable to the static types of the arguments; at run time the JVM executes the override of that exact signature in the dynamic type of x.

Statement

Two phases.

  1. Compile time: look at the static type of x and at the static types of the arguments. Among the methods named f visible in (declared or inherited) that are applicable, pick the most specific signature . If none or more than one is maximal, compilation fails.
  2. Run time: let be the dynamic type of the object. Starting from and moving up the hierarchy, execute the first method with exactly the signature .

Static, private and final methods and constructors are bound at compile time.

Example

Derivation

For x.m(y): the static type of x is A, whose only method is m(A), applicable because B is a subtype of A, so =m(A)=. The dynamic type is B, which overrides m(A): B.m(A) runs. B.m(B) is never considered, because the signature was fixed in phase 1.

Intuition

The compiler chooses which message is sent; the object chooses how to answer it.

Pitfall

Writing equals(Point p) instead of equals(Object o) adds an overload: collections call equals(Object) and never see it.
