#+TITLE: cerebro

A personal, second-brain for mathematics: rigorous notes in English,
written in Org-mode/Org-roam, exported to LaTeX through a parametric
pipeline, in an environment isolated and pinned with GNU Guix. Meant to
last through a mathematics degree, a PhD, and an academic career after
that -- so everything here favours plain text, GNU tools, and things
that are easy to understand years from now over anything clever.

* Principles

- Plain text, versioned in git. No proprietary formats, no cloud
  services, no databases you can't read with a text editor. The
  "pattern-finding" query system (see below) is local, structural graph
  queries over your own notes -- deliberately not embeddings or a cloud
  service, which would break this principle.
- Isolation means Guix, not MELPA/straight.el at runtime. Every Emacs
  package -- and Taskwarrior, Timewarrior, jq, GnuPG -- comes from
  =guix.scm=; nothing is fetched from the network when Emacs starts.
- Reproducibility means a pinned Guix channel (=guix/channels.scm=),
  not just "uses Guix". Without a pin, the same commands can give you
  a different environment next year.
- Hooks are thin wrappers around =make= targets. The logic lives in
  the makefile, testable by hand; a hook only calls =make=. This is
  also the entire "CI/CD": local only, no forge dependency. *Every gate
  is measured in seconds*: a parse check in =pre-commit=, the test suite
  in =post-commit= (=make test=), tests + graph-wide lint in =pre-push=
  (=make check=). The LaTeX profile matrix is deliberately *not* on any
  hook -- fourteen TeX compiles before a push is a gate people learn to
  bypass with =--no-verify=, which is worse than no gate. It is
  =make export-matrix= (or =make ci=), run when you touch =latex/=, the
  export profiles or the course generator.
- One Org source, many LaTeX/PDF variants -- never duplicated content.
  See "Parametric export" below.
- One source of truth per domain: notes live in Org/Org-roam, tasks
  and deadlines live in Taskwarrior, time lives in Timewarrior. The
  bridges between them are explicit, one-way scripts, not
  bidirectional sync.
- The tag taxonomy, export profiles, and LaTeX theorem environments
  are all *data* (an alist entry, a tag, a =#+NAME=) read by a handful
  of general mechanisms, not one bespoke code path per feature -- this
  is what "parametric" means here, and it's what keeps the whole thing
  KISS despite doing a lot.

* Bootstrap

Manual, one-time steps this repo cannot script for you:

1. Install Guix itself, if not already installed: follow the official
   manual's binary installation for a foreign distribution --
   https://guix.gnu.org/manual/en/html_node/Binary-Installation.html
2. After installing, run =guix pull= once, then regenerate the pin:
   =guix describe -f channels > guix/channels.scm= and commit it.
   Until you do this, =guix/channels.scm= is a template and
   =bin/guix-run= falls back to running unisolated with whatever is on
   PATH, with a loud warning (see the comments in that file) -- this is
   what let the very first commit to this repo happen before Guix was
   installed at all.
3. =direnv allow= in this directory. Note: =guix= itself is usually
   only on PATH in an interactive shell that sources
   =/etc/profile.d/guix.sh= (or equivalent) -- =bin/guix-run= also
   checks =~/.config/guix/current/bin= and =~/.guix-profile/bin=
   directly, so hooks and scripts work even from a shell that hasn't
   sourced that profile snippet.

Then:

- =make bootstrap-check= -- reports which prerequisites are present.
- =make shell= -- drop into the isolated environment interactively.
- =make install= -- symlinks the =cerebro= CLI into =~/.local/bin=,
  wires up the versioned git hooks (=git config core.hooksPath
  githooks=), and symlinks =taskwarrior/hooks/*= into =~/.task/hooks/=.

Once =direnv allow=-ed, plain =emacs= typed in a terminal inside this
directory also picks up the project's =.emacs.d= (via =bin/emacs=,
shadowing the real binary on PATH -- see that file and =.envrc='s
=PATH_add bin= for how/why this is safe). Every other =bin/= script
also becomes callable by its bare name this way (=cerebro-issue "..."=
instead of =bin/cerebro-issue "..."=).

* Two modes: =math= and =dev=

There are exactly two reasons to open this repository, and they want
opposite editors.

| Mode   | What it is for                                       | The archive | The machinery | A note opens | Issues shown                             |
|--------+------------------------------------------------------+-------------+---------------+--------------+------------------------------------------|
| =math= | study, write mathematics, compile documents          | writable    | read-only     | =write=      | mathematical ones + everything untagged  |
| =dev=  | maintain the modules, tools, tests, LaTeX classes    | writable    | *writable*    | =source=     | machinery ones + everything untagged     |

Before this existed, the difference was a set of habits: you remembered
to =C-c H u= before editing a module, you filtered the backlog by eye,
and nothing on screen said which of the two jobs you were doing. It is
now one binary setting, held in one place
(=.emacs.d/lisp/cerebro-mode.el=) and /visible/ -- the status line and
the start page both say which mode is in force, because in =dev= every
file in the repository is writable and that is not a thing to be wrong
about.

Everything that differs is one row of data per mode: what may be written
(handed straight to =cerebro-isolation.el=), how a note opens
(=cerebro-study.el=), which issues are yours, and which keys the start
page advertises. Adding a /dimension/ is adding a key to that table and
a clause in =cerebro-mode-apply=, the one function that knows how any of
it is switched on. Nothing else in the config is mode-dependent: the
keys, the note format, the export profiles and the results graph are
properties of the archive, not of the person in front of it.

From the editor (=C-c M=, a capital prefix like =C-c G= and =C-c B=
because it is infrastructure):

: C-c M m   math -- the archive is writable, the machinery is not
: C-c M d   dev  -- every file in the repository is writable
: C-c M t   toggle: with two modes, "the other one" is unambiguous
: C-c M s   what is in force, what it permits, and where it came from

Each takes =C-u= to change this session only. From the shell:

: cerebro mode            # what is in force, and why
: cerebro mode dev        # ...and remember it for every later session
: cerebro math            # open the editor in math, just this once
: cerebro dev             # ...or in dev (CEREBRO_MODE, one session)

Resolution order is =CEREBRO_MODE= > the remembered mode
(=.emacs.d/var/mode=, one word, gitignored -- which job you are doing
today is not part of the second brain) > the default, which is =math=,
because maintaining cerebro is the exception and the exception is the
one you should have to ask for.

** Which issues are whose

The tracker stays /one/ file (one source of truth per domain), so the
split is by tag: an issue tagged =:guix:ci:= is machinery, one tagged
=:research:= or with any area tag (=analysis=, =algebraic_geometry=, ...
read from =cerebro-taxonomy.el=, never copied) is mathematics.

The rule that matters is the third case: *an issue tagged for neither
mode belongs to both*. The filter may only hide what explicitly says it
is the other job -- an issue you cannot see is an issue you conclude you
never filed, which is the same failure the note finder refuses. It also
says what it hid (on stderr, so the listing stays machine-readable), and
=--all-modes= turns it off:

: cerebro issue list                  # this mode's work
: cerebro issue list open --all-modes # everything
: cerebro issue close <id>            # never filtered: an id you can name, you can close

The start page follows the same rule -- and the census line under the
banner still counts /all/ open issues, so the number never silently
shrinks with the mode.

* Command-line workflow

Everything is scriptable from the terminal through one git-style
dispatcher, =bin/cerebro= (=make install= links it to =~/.local/bin/cerebro=;
bare =cerebro= opens the editor). One implementation per operation, so the
shell and the editor never drift -- Emacs binds keys straight onto these
(=C-c d ...=, see =cerebro-cli.el=).

: cerebro help                              # every subcommand
: cerebro mode [math|dev]                    # which of the two jobs (see "Two modes")
: cerebro math / cerebro dev                 # open the editor in one, this session only
: cerebro issue new "title" [-p A] [tags]   # create (logged in issues/issues.org)
: cerebro issue list [open|all|done] [tag] [--all-modes]  # this mode's work by default
: cerebro issue show|close|start|reopen <id|query>
: cerebro issue note <id|query> "text"      # append a timestamped progress note
: cerebro issue next                         # the single most urgent open issue
: cerebro issue scan                         # create issues from CEREBRO-ISSUE: markers
: cerebro issue report                       # counts by state and tag
: cerebro note new "title" [tags] [msc]     # create, born classified (:ID:, :seed:)
: cerebro note find QUERY                    # search by title/body
: cerebro note rehash                        # re-derive every notes/math/ file name
: cerebro today                              # the morning-review agenda
: cerebro results [index|check|open|deps|dependents] [NAME]
: cerebro query <hubs|orphans|by-tag|...>    # org-roam graph
: cerebro lint  /  cerebro stats  /  cerebro doctor  /  cerebro env
: cerebro time [today|week|month]            # timewarrior summary
: cerebro time start [tags...] | stop        # clock dev time (tagged `cerebro')
: cerebro task [args...]  /  cerebro sync    # taskwarrior; refresh the Org bridge
: cerebro export FILE PROFILE [TARGET]       # compile one note to PDF
:     # PROFILE required: syllabus|lecture|slides|handbook|conjecture|single

Fast by design: the pure-Emacs/POSIX subcommands (=issue=, =note=,
=mode=, =results=, =stats=, =today=, =lint=) run on the tools on =PATH=;
only the ones that truly need the pinned environment (=query='s Org-roam
DB, =time=/=task='s timew/task, =export='s LaTeX) go through
=bin/guix-run=. Inside =make shell=, the =cerebro= launcher or direnv --
where you normally are -- the Emacs on =PATH= /is/ the pinned one, so
this costs nothing there and saves ~90 s of channel resolution
everywhere else. =lint= is in the first list because it already degrades
by design (no aspell = no spelling pass, no Org-roam = no tier-2 graph
checks, each announced); =CEREBRO_GUIX_FORCE=1= puts any of it back
through the pinned profile deliberately. The issue lifecycle is plain Org editing done through
org-mode itself, so =close= logs a =CLOSED= timestamp and =note= appends a
committed work log, exactly as they would interactively, and everything
stays in =issues/issues.org=.

Two conveniences worth knowing. *Auto-generated issues*: drop a
=CEREBRO-ISSUE: <title>= marker in a code comment where you notice
something to fix; =cerebro issue scan= turns each into a tracked issue
(tagged =from-code=, with the source location noted), idempotently -- it
only appends, never rewrites your source. *Time on an issue*: either
=org-clock-in= on its heading (=cerebro-time.el= mirrors that into =timew=)
or =cerebro time start=/=stop= from the shell; =cerebro time= then reports
it. Every command is also a keybinding (=C-c d ...=, see cerebro-cli.el)
and an =M-x=.

* Parametric export

: make export FILE=notes/courses/analysis-A.org PROFILE=syllabus
: make export FILE=notes/courses/analysis-A.org PROFILE=lecture
: make export FILE=notes/courses/analysis-A.org PROFILE=slides
: make export FILE=notes/courses/analysis-A.org PROFILE=handbook
: make export FILE=notes/conjectures/<hash>.org PROFILE=conjecture
: make export FILE=notes/README.org PROFILE=single TARGET=thm-uniqueness-of-limits

One Org source, four documents, composed from two independent axes in
=.emacs.d/lisp/cerebro-latex.el= (=cerebro-latex-content-modes= x
=cerebro-latex-doctypes= -> =cerebro-latex-profiles=): which blocks
survive, and which class typesets them. Adding a named preset is a
one-line addition to that alist, not new code.

There are *four*, one per audience, because a course has four audiences
and every further variant was a document nobody built:

| Profile    | For                                         | Content kept                                            | Class                        |
|------------+---------------------------------------------+---------------------------------------------------------+------------------------------|
| =syllabus=   | what the course /is/ (the course file itself) | everything                                              | cerebro syllabus             |
| =lecture=    | what I say at the board                     | statements + proofs; drops remarks                      | cerebro article              |
| =slides=     | what the room sees                          | statements only -- no proofs, no prose                  | cerebro-beamer               |
| =handbook=   | what the student keeps                      | everything, + appendices + an index                     | cerebro book                 |
| =conjecture= | my open questions                           | everything                                              | cerebro article, *two columns* |
| =single=     | one theorem to study                        | one =#+NAME='d block + adjacent proof                     | cerebro article              |

The table used to have fourteen rows (=full=, =statements=, =report=,
=manual=, =dispensa=, =handout=, =exercises=, =problems=, an =amsart=
=paper=/=preprint= pair and two aliases). Thirteen of them compiled on
every =make ci= and four of them were ever read. Cutting the list is the
same decision as everything else here: fewer mechanisms, each one
load-bearing.

Two of the four are worth a note of their own.

*=slides= is minimal by construction, not by discipline.* Its content
mode keeps only the statement blocks (definition, theorem, lemma,
proposition, corollary, axiom, notation, conjecture) and prunes the
connecting prose -- the paragraphs that make a note readable are exactly
what makes a slide unreadable. You say the prose; you project the
statement.

*Nothing on a slide can overflow its frame.* Three mechanisms, because
there are three ways to overflow one: the export puts one frame per
/note/ rather than per chapter (=:headline-levels 2=); a frame that still
does not fit is broken across slides (=allowframebreaks=) instead of
running off the bottom edge; and every figure is wrapped in
=\cerebrofit=, an adjustbox that shrinks -- never enlarges -- a
tikzpicture or pgfplots axis until it fits the frame. A page-sized
diagram dropped unchanged onto a 12.8cm slide, drawn straight over
whatever came next, was the failure this replaced.

*The handbook is a book, and gets what a book has.* An analytical index
at the end, built from the notes' own =#+NAME='d results
(=def-supremum= indexes "supremum") plus any =#+INDEX:= a note adds by
hand -- so the index is derived from something the archive already
requires and cannot fall out of date. Appendices come from an optional
=* Appendices= section in the course file, composed after =\appendix=
and therefore lettered. Both are parametric: the class decides whether
there *is* an index (=\index= is inert in the other profiles, so a note
carrying entries still compiles as a lecture sheet or a deck), and the
course decides what is an appendix -- no note has to know.

*=conjecture= is the one profile that is not about a course*: it
typesets =notes/conjectures/= as a two-column article, same class, same
macros, same theorem suite.

All six profiles are compiled end to end by =make export-matrix= (the
manual, thorough gate), together with all four documents of a real
course.

Two orthogonal class toggles are derived from the content, not written
by hand: =proofs=/=noproofs= (does a =#+begin_proof= body survive) and
=solutions=/=nosolutions= (does a =#+begin_solution= body survive), so a
single exercise sheet prints with or without worked solutions from one
source.

=single= extracts exactly one =#+NAME='d theorem-like block plus an
immediately following sibling =proof= block ("a focused sheet to
study"), discarding everything else in the file, by simple adjacency
-- not a dependency graph.

Notation (\R, \abs{}, \eps, TikZ/pgfplots/tikz-cd, cleveref, ...) lives
once in =latex/cerebro-macros.sty=, shared by every class. Citations
(=[cite:@key]=, via Org's own =org-cite= + biblatex) resolve against
the single shared =bib/references.bib= in every doctype; slides load
biblatex too but don't auto-print a reference list (beamer needs it
inside its own =frame=, add one by hand with a raw LaTeX export
snippet if a deck needs one).

Conventions for note authors, load-bearing for all of the above --
getting these wrong fails silently, not loudly (see =notes/README.org=
for the full list, worth reading once):
never set =#+LATEX_CLASS=/=#+LATEX_CLASS_OPTIONS=/=#+EXCLUDE_TAGS= in a
note file; write special block names lowercase; use =\(...\)= for inline
math and =\[...\]= for display -- *never bare =$...$=* (a =$= next to
punctuation, e.g. =$x$--$y$=, silently mis-parses in Org into a literal
dollar that then fails to compile; the linter rejects any naked =$=); keep
display equations on one line starting with =\[=, not =|=; put
meta-commentary in a =#+begin_comment= block, not plain prose (a plain
paragraph before the first heading becomes its own slide in the =slides=
profile).

* How a document looks

Every export, from a one-theorem note to a bound handbook, is the same
document family: same title page, same links, same metadata. That is
what =latex/cerebro.cls= is for, and three things in it are worth
knowing.

- *A title page of its own.* =\maketitle= is redefined to a full
  =titlepage=: a drawn mark (three orbits and a dot -- TikZ, no image
  file, scales with the page), a rule, the title, an optional subtitle,
  the author, the date, and the version at the foot. One look for
  everything: a syllabus, a handbook and a single result should be
  recognisably from the same archive.
- *Author and version, filled in by the exporter.* The author comes from
  =cerebro-latex-author= (a person's name -- git's =user.name= here is a
  forge account, which is the wrong thing on a document you hand to
  someone); the version from =git describe --tags --always --dirty=, so
  a PDF built from uncommitted edits says =-dirty= on its title page.
  Neither is something a note has to carry.
- *Links that are not boxes.* Org loads hyperref with no options, which
  gives every reference and citation a coloured rectangle -- invisible
  on paper, ugly on screen, and this archive is read on screen. The
  class loads hyperref first, with =colorlinks= and three muted colours
  (references, citations, URLs), so Org's later =\usepackage{hyperref}=
  is a no-op.

The date is formatted too: =[2026-07-29 Wed 13:55]= is right in a file
and wrong on a title page, so the exporter turns it into =29 July 2026=.

** Builds happen in =.build/=

A LaTeX compile produces a dozen files -- =.aux=, =.log=, =.fls=,
=.fdb_latexmk=, the generated =.tex= itself -- and they used to land next
to the note. They were gitignored, but a directory of mathematics should
contain mathematics: =ls notes/math/= answering with build rubbish is how
a source tree stops being readable.

Now every build goes to a =.build/= directory beside the source, *PDF
included*, and one function decides that for the whole config
(=cerebro-latex-output-file=) -- =C-c e e=, =make export= and
=bin/cerebro-course-export= all ask it rather than guessing. Course
documents are then collected into =out/= under their own names. Both
directories are gitignored, and =make clean= removes them.

* Courses as an index over the notes

: bin/cerebro-course analysis-B "Mathematical Analysis B"    # scaffold one file
: bin/cerebro-course-export notes/courses/analysis-B.org     # its four documents

A course here owns *no mathematics of its own*. It is an ordered index
into =notes/math/=, and that is the whole model: you write the atomic
notes first, and a course -- or a book -- is the decision of what to
teach in which order.

*One file per course*, =notes/courses/<slug>.org=, written by hand:
metadata (=#+COURSE_TITLE=, =#+TERM=, =#+LEVEL=, =#+PREREQS=,
=#+TEXTBOOK=, =#+MSC=, ...), the course prose, a =* Programme= section
listing the course's notes in teaching order as =id:= links (=C-c n i=
inserts one), and an optional =* Appendices= section written the same
way.

The other three documents are *composed* from it at export time: the
programme's sub-headings become chapters, every link becomes an Org
=#+INCLUDE= of the note it points at (front matter skipped, so a note's
=#+TITLE= cannot override the document's), and the appendices are
emitted after =\appendix=. The composition lands in =.build/= beside the
course -- gitignored, like every other build product.

There used to be a second, committed file (=book.org=) that had to be
regenerated before compiling. Removing it removed three things at once:
a generated file in git, a step to remember, and the failure mode where
you compile a book that no longer matches its programme.

#+begin_example
  * Programme
  ** Continuity
  - [[id:...][Limits and continuity]]
  ** Inner product spaces
  - [[id:...][Inner product space]]
  - [[id:...][Cauchy--Schwarz inequality]]
#+end_example

What this buys, and why it is worth a composer:

- *No second copy.* The old model put lecture notes inside the course
  directory, so the same mathematics existed twice -- once as an atomic
  note, once as course prose -- and the second copy was the one that
  rotted. Now correcting a proof once corrects every course that teaches
  it, including the one you taught last year.
- *Reuse.* One note can appear in several courses; a note that turns out
  to belong in two places is not a problem to solve.
- *Nothing breaks.* The programme refers to notes by =:ID:=, so renaming
  or moving one touches no course -- which matters more than it used to,
  since a note renames itself whenever its metadata changes. A link to a
  note that no longer exists is *reported* and left visible in the
  document as =# MISSING NOTE:= -- a chapter cannot vanish silently.
- *The reading order is a teaching decision*, made in the syllabus,
  rather than a filing decision made in a directory listing.

** Every document, from one file

: bin/cerebro-course-export notes/courses/analysis-A.org         # all four, zipped
: bin/cerebro-course-export notes/courses/analysis-A.org slides  # just one

| Key       | What                                                        |
|-----------+-------------------------------------------------------------|
| =C-c e c= | build *one* document of this course and show it              |
| =C-c e a= | build *all* of them and zip them (the file you hand over)     |
| =C-c e p= | open one already built, without rebuilding                   |
| =C-c e o= | open a course to edit                                        |

Four documents come out of that one file, one per audience: =syllabus=
(whoever is deciding whether to take the course), =lecture= (me, at the
board), =slides= (the room), =handbook= (the student, at home). What
this adds over a plain =make export= is naming: the exporter writes its
PDF beside the source it compiled, so =handbook= and =slides= -- both
composed from the same course -- would otherwise be the same file, each
overwriting the last. They are collected into =notes/courses/out/= as
=<course>-<output>.pdf=, gitignored, plus =<course>.zip=: one file with
all four in it, for handing the course to someone.

Single notes still compile straight from =notes/math/= with any profile.
See =notes/courses/analysis-A.org= for the worked course: 22 notes,
eight chapters, two appendices, all four documents.

(The =handbook= doctype maps an outline level 1 to =\chapter=, since its
base class -- scrbook -- has one: that is what makes a generated book
number its chapters =1=, =2= rather than as sections of a chapter that
never comes.)

* Previews are sized against the font, not by a constant

A rendered formula should be the same optical size as the sentence it
sits in, and a figure should belong to the measure of the text it
interrupts. Both are derived from the body size
(=cerebro-theme-font-size=) and recomputed whenever it changes, so
=C-c u += moves formulas, figures and prose together.

Getting the formula right needs one fact about Org that is easy to miss:
it hands the converter *either* a resolution (=%D=) or a scale (=%S=),
depending on which the program takes, and the two are different
regimes. dvipng rasterises at the given dpi, so the display's own
resolution cancels and matching the text is just =body / 10pt=. dvisvgm
is given a pure magnification of a document it emits in *points* (the
SVG it writes carries =width=51.55pt=, not pixels), so the fragment and
the prose are both physical sizes and the scale wanted is again a ratio
of two point sizes. Which regime a backend is in is read from its own
converter command in Org's table, and its size multiplier from the same
table, so nothing here is a second copy of a number Org owns.

The catch, and the bug that lived here longest: Org has *already*
multiplied by the display resolution on the way to =%S=, so the =:scale=
handed to it must divide that back out. The old code multiplied by it
instead, putting the display dpi *squared* into what dvisvgm received.
Since =dpi²/(72×140)= is 0.91 at 96dpi, it looked right on the machine
it was fitted on and grew quadratically everywhere else -- 2.5x too
large at 157dpi, 3.7x at 192dpi. On a HiDPI screen every formula came
out enormous. The invariant that kills this class of error outright is
now a test: *the magnification the converter receives must not depend
on the display at all*, and no correct derivation of it contains the
resolution twice.

** Previews are fast because the preamble is compiled once

Org runs LaTeX once per fragment, and this preamble is small to read and
enormous to execute -- =cerebro-macros.sty= pulls in amsmath, amssymb,
mathtools, tikz, tikz-cd and pgfplots, 33 =.sty= files in all -- so
every inline =\(\eps\)= used to pay two thirds of a second to load a
plotting library it did not use. Forty fragments in a note was half a
minute of frozen Emacs, which is why previews felt unusable.

The fix is LaTeX's own: dump the executed preamble into a format file
once (=mylatexformat=, part of texlive) and start every later run from
it. Measured, same fragment, same output:

| plain preamble     | 663 ms/run |
| precompiled format | 202 ms/run |

Deliberately *one* format, holding the whole preamble including the
graphics packages. A second, math-only format measured 160 ms -- another
20% -- and would have cost a per-fragment classifier deciding which
format a fragment needs, plus a wrong answer rendering a =tikzpicture=
against a preamble without tikz. The premise of this module is that the
preview and the export agree; splitting the preamble is exactly how to
lose that, for 40 ms.

It is built on the *first preview*, not at startup (a second of frozen
Emacs to speed up something the session may never do is a bad trade),
and cached under =.emacs.d/var/texfmt/=.

*A .fmt is a binary artefact of the TeX that wrote it*, and that is the
sharp edge of this whole idea. A format dumped by the system TeX Live
and then read by the pinned Guix one is rejected outright: latex aborts
producing nothing, and Org reports =File "/tmp/orgtexXXXX.dvi" wasn't
produced. Please adjust `dvisvgm'= -- naming the one component that is
not at fault. Every preview in the buffer fails, and the message sends
you the wrong way.

Two things make that impossible rather than merely recoverable:

1. *the engine is an input to the staleness signature* (=latex
   --version= and its path, since two TeX Lives of the same version in
   different profiles still write incompatible formats), so a different
   TeX means an automatic rebuild, not a mismatch;
2. *a cached format is verified, never trusted*. Before it is handed to
   Org, one short fragment is compiled through it; if no =.dvi= appears
   -- wrong engine, truncated file, anything -- the format is treated as
   absent and rebuilt, and if that fails too, previews simply compile
   the plain preamble. One ~200 ms run per session, and the failure mode
   is *slow*, never *broken*.

=C-c u R= forces a rebuild by hand; with the above it should never be
necessary. =cerebro-preview-status= reports which path is in use, which
engine, and why.

** Tuning it

| =C-c u ]= / =C-c u [= | formulas 10% larger / smaller *relative to the prose* |
| =C-c u += / =C-c u -= | the body text, formulas following along               |
| =C-c u R=             | rebuild the precompiled format                        |
| =C-c u P=             | the resolved scale, the speed path, the figure width   |

=cerebro-preview-relative-size= is the same knob as =C-c u ]= in a
defcustom; generated figures are =cerebro-preview-figure-columns=
characters wide (60 by default) rather than a pixel constant that meant
one thing at 12pt and another at 18. =M-x cerebro-preview-status=
reports the scale it computed *and the one it wanted*, side by side, so
a sizing complaint is a number you can read rather than an impression.

* Subject classification

Two orthogonal dimensions, both data, both checked/queried by the
tooling -- "roughly what shelf" for daily navigation, "exactly what
leaf" for papers.

- *Area hierarchy* (=.emacs.d/lisp/cerebro-taxonomy.el=): a two-level
  tree of tags rendered as Org's own /group tags/, so a supertag
  expands to its members -- filtering the agenda or a query by
  =analysis= also catches a note tagged only =functional_analysis=.
  Covers the field from =algebra= and =geometry= through
  =mathematical_physics=. Add an area in one line there; the linter
  vocabulary and the agenda grouping both follow.
- *MSC2020* (=.emacs.d/lisp/cerebro-msc.el=): the AMS Mathematics
  Subject Classification, recorded per note as a =#+MSC:= keyword
  (=#+MSC: 47A75, 46C05=). It is the plain-text standard, spans all of
  mathematics, and is what a journal requires -- so the same code that
  files a note into the lifelong database fills =\subjclass[2020]{...}=
  in any submission. The linter validates every code against MSC2020;
  =make query Q=by-msc ARGS=46= lists everything under a class, with its
  name; =make stats= reports classification coverage.

* Citations: one bibliography, and a linter that checks it

: C-c b i    insert [cite:@key], completing over author / year / title
: C-c b n    add a new entry -- it asks for the fields and generates the key
: C-c b y    import a BibTeX entry from the kill ring, re-keyed
: C-c b o    open what the citation at point points at
: C-c b f    open the bibliography

*There is exactly one bibliography*: =bib/references.bib=, for the whole
archive. Not one per course, not one per paper. A reference is a fact
about the literature, not about the document that happens to cite it,
and the moment there are two files the same book acquires two keys and
the archive stops being able to answer "where else did I read this?".
The path is a constant in =cerebro-org.el= because three layers need the
same answer: the exporter (=org-cite-global-bibliography=), the editing
surface (=cerebro-bib.el=), and the linter.

*Keys are generated, not invented*: surname + year + first meaningful
word of the title (=rudin1976principles=), suffixed =a=, =b=, ... when
that is already taken. =C-c b n= asks for the fields the entry type
actually needs (=cerebro-bib-entry-types=, data), omits the ones you
leave blank rather than writing =doi = {}=, and appends the entry to the
one file. =C-c b y= does the same for an entry someone sent you, so the
bibliography has one naming convention rather than one per source.

*And the check that makes the rest trustworthy*: =cerebro lint= reads
every =[cite:@key]= in every note and *fails* on a key the bibliography
does not define. A wrong key used to typeset as a bold =[key?]= in the
middle of a paragraph and be mentioned only in a =.blg= nobody reads;
now it is a push that does not happen.

The powerful half is optional, like everything else from =guix.scm=:
with =emacs-citar= present, =C-c b i= completes over author/year/title
with an indicator for what has a PDF or a note, citations are fontified
and clickable in the buffer (org-cite's insert/follow/activate
processors are all citar), and =embark= makes a candidate actionable.
Without it, org-cite's own processor completes over the keys and every
command above still works -- the syntax in the file is Org's, not a
package's.

Deliberately offline: nothing here fetches a DOI or searches a database
(invariant: no runtime network). A reference typed once, into one file,
checked by the linter, is worth more than one auto-fetched into three.

* Tags

A small, controlled vocabulary (data in =org-tag-alist=, in
=.emacs.d/lisp/cerebro-org.el=), not free text: maturity
(=seed=/=growing=/=evergreen=), difficulty
(=easy=/=medium=/=hard=), epistemic status
(=conjecture=/=folklore=/=open_problem=), the area hierarchy spliced in
from =cerebro-taxonomy.el= (see "Subject classification" above), and two
*functional* tags that change tool behavior rather than just describing
the note: =crypt= (encrypted, see below) and =drill= (spaced-repetition
flashcard, see below). See =notes/README.org= for what each one means --
the epistemic-status ones are structural, not just descriptive: see
"Consistency checks" below. =evergreen= is also what
=bin/cerebro-publish-garden= (see "Digital garden") picks up.

* Consistency checks

: make lint
: bin/cerebro-lint [file.org ...]

=bin/notes-lint.el=, wired into =githooks/pre-push= (not =pre-commit=
-- graph-wide checks don't belong on the fast path of every commit).
Hard errors: duplicate =#+NAME= labels (would silently break LaTeX
compilation), a =theorem=/=lemma=/=proposition=/=corollary= block with
no adjacent =proof= and no =conjecture=/=folklore=/=open_problem= tag
on its heading, headings using tags not in =notes/README.org='s
vocabulary, an =#+MSC:= code that is not valid MSC2020 (would mis-file
the note and break =\subjclass= on a paper), the results-graph errors
(a =#+NAME= reused as a result key across the corpus, a =#+DEPENDS= on a
result no note defines, or a dependency cycle -- see "Results layer"),
and -- when the Org-roam database is available -- broken =id:= links. Informational only, never
fails the check: an =evergreen= note with no =#+MSC:= yet, orphaned
nodes (normal for a fresh =seed= note), and possible misspellings (prose
extracted from =#+begin_.../#+end_...= blocks and =#+KEYWORD:= lines,
checked with aspell/hunspell -- false positives on jargon/proper nouns
happen, hence advisory-only).

* Query system

: make query Q=hubs
: make query Q=by-tag ARGS=evergreen

=.emacs.d/lisp/cerebro-query.el= (also =M-x cerebro-query-*=, =C-c q
...=), built on Org-roam's own =org-roam-db-query=: =orphans=, =hubs=
(ranked by backlink count -- your load-bearing concepts), =stale-hubs=
(a hub nobody has touched in a while -- foundational but neglected),
=co-citation= (two notes never linked to each other directly, but both
linked from many of the same third notes -- a structural pattern the
backlink view of either note, alone, won't show you), =by-tag=, and
=by-msc= (notes whose =#+MSC:= matches a code or two-digit class, e.g.
=make query Q=by-msc ARGS=46= for everything under functional analysis
-- a plain file scan, so it works before a note is even linked in).
Local and structural on purpose, not embeddings or a cloud service.

Run from the command line (=make query=), the batch entry point calls
=org-roam-db-sync= first: interactively the autosync mode keeps the
SQLite cache current, but a bare CLI query would otherwise report
structure from a stale database (notes edited in any editor since the
last sync). =bin/notes-lint.el='s tier-2 graph checks do the same. The
pure counting/joining behind all of these lives in
=.emacs.d/lisp/cerebro-graph.el= (no Org-roam dependency), unit-tested
directly by =tests/cerebro-graph-tests.el=.

* Results layer (logical dependencies)

: make results                         # the global index of named results
: make results CMD=check               # cycles / dangling / duplicate names
: make results CMD=deps       NAME=thm-heine-borel
: make results CMD=dependents NAME=def-compact

For a theoretical mathematician the notes /are/ a dependency structure:
a theorem rests on lemmas and definitions, which rest on axioms and
earlier definitions. =.emacs.d/lisp/cerebro-results.el= makes that
structure a queryable, acyclic graph, on top of the =#+NAME= a result
block already carries (the same key the =single= export and the linter's
duplicate check use), with *one* added convention and nothing else:

: #+DEPENDS: def-compact, thm-bolzano-weierstrass
: #+NAME: thm-heine-borel
: #+begin_theorem
: ...
: #+end_theorem

Order matters: =#+DEPENDS= goes /above/ =#+NAME=, and =#+NAME= stays
directly on top of the =#+begin_= line. =#+DEPENDS= is not an Org
affiliated keyword, so placing it between =#+NAME= and the block would
detach the name (breaking the =single= export); the linter's
unnamed-result advisory catches that if you slip.

=#+DEPENDS:= lists, comma/space separated, the =#+NAME=s this result
rests on. It is *invisible to every export profile* -- Org drops unknown
keywords, exactly as it does =#+MSC:= (verified against a real compile)
-- so declaring dependencies never changes a single PDF; it only builds
the graph. This is a third, distinct query surface:

- =cerebro-query.el= (Org-roam DB) -- /how notes cite each other/
  (backlinks, hubs, co-citation).
- =cerebro-results.el= (this) -- /on what a result logically rests/
  (=thm= -> =def= -> =axiom=), across files.
- =cerebro-ql.el= (org-ql) -- /which entries match criteria right now/
  (tags, TODO state, timestamps).

Interactively (=C-c r=): =C-c r i= index, =C-c r d= dependencies of a
result (foundations first), =C-c r r= its dependents (the impact /
backlink view -- "if I change this definition, which proofs are
affected?"), =C-c r c= the consistency check. The parsing and the graph
algorithms (topological reachability, cycle detection) are pure -- no
Org-roam, no Guix -- so the whole layer works outside the environment too
and is unit-tested directly by =tests/cerebro-results-tests.el=.

*Conventions*, load-bearing: name a result you want to reference with a
*globally unique*, kebab-case key (=thm-...=, =def-...=, =lem-...=,
=prop-...=, =ax-...=), and only reference existing =#+NAME=s in
=#+DEPENDS=. The linter (below) enforces all three -- a duplicate name, a
=#+DEPENDS= on a name no note defines, and any dependency cycle are hard
errors. Referenceable result types: =theorem=, =lemma=, =proposition=,
=corollary=, =definition=, =axiom=, =conjecture= (proofs and apparatus
are not results you depend on). See =notes/courses/analysis-A.org= for a
worked =#+DEPENDS= example.

** Proof status: what the archive owes

Every result carries a state -- =proved=, =assumed= or =open= -- and two
of the three are inferred, so the common case costs no typing:

- a statement with a =#+begin_proof= directly after it is =proved= (that
  adjacency is already this repo's convention: it is what the =single=
  export profile keeps);
- anything else that ought to have a proof (theorem, lemma, proposition,
  corollary) is =open=;
- =#+STATUS: assumed= says it out loud, above =#+NAME:= like
  =#+DEPENDS:=, and always wins over the inference.

: C-c r o          what still owes a proof (open first, then assumed)
: cerebro results open

=assumed= is the one that earns its keep. A second brain accumulates
results used before they are proved, and the difference between proving
something, deciding to assume it, and simply not having got to it is the
difference between mathematics and wishful thinking -- written down, it
becomes a list you can work through instead of a feeling.

** Note maturity, as an operation

: C-c m s   set this note's maturity (seed | growing | evergreen)
: C-c m +   one rung up

=:seed:= -> =:growing:= -> =:evergreen:= was always in the taxonomy; what
was missing was a way to *change* it, and a state nobody can change with
a keystroke is a state nobody updates. Promotion is one-way by design --
demoting a note is a deliberate act, so it is an edit. The start page
lists the oldest seeds, which is where they go to be forgotten.

* Saved views (org-ql)

=.emacs.d/lisp/cerebro-ql.el= (=emacs-org-ql= from =guix.scm=) is the
second query surface, and deliberately a different tool from the graph
queries above:

- =cerebro-query.el= (Org-roam DB) answers *structural* questions --
  backlinks, hubs, orphans, co-citation: /how the corpus is wired
  together/.
- =cerebro-ql.el= (org-ql) answers *content/metadata* questions -- by
  tag, TODO state, timestamp, property, across every note: /which
  entries match these criteria right now/.

The saved views are data (=org-ql-views= entries -- one alist line
each): seeds & growing (the maturity backlog), drill cards, conjectures
& open problems, hard notes, active work (=TODO=/=DOING=), and
recently-touched. =C-c v v= (=M-x org-ql-view=) picks one; =C-c v s= is
an ad-hoc search; =C-c v a= (=cerebro-ql-area=) lists every entry in an
area, expanding the supertag to its whole family
(=cerebro-taxonomy-family=, unit-tested) so an =analysis= query also
catches =functional_analysis=. No =org-super-agenda= dependency is used.

* Writing notes: capture, IDs, dailies

- *Capture* (=C-c n c=, templates in =cerebro-roam.el=): note /
  definition / theorem / flashcard, each born *classified* -- a =:seed:=
  maturity tag and an empty =#+MSC:= line ready to fill in, so nothing
  enters the database unfiled. Separately, =C-c c= (plain =org-capture=,
  template in =cerebro-issues.el=) files an *issue* into
  =issues/issues.org= in the same heading shape =bin/cerebro-issue=
  produces (see "Issues"), with a link back to where you were -- so a
  distraction becomes a tracked issue without leaving the note.
- *Links by ID* (=cerebro-org.el=): links prefer a node's =:ID:= over
  its path (=org-id-link-to-org-use-id 'use-existing=), so a note keeps
  resolving after it is renamed or moved -- essential for a database
  meant to be reorganized many times over a career. The id<->file cache
  (=.org-id-locations=) is gitignored, rebuilt from the notes.
- *No daily notes.* org-roam-dailies is deliberately not enabled and
  =notes/daily/= is gone: the unit of this archive is a *result*, not a
  day, and a dated file is the one kind of note nothing ever links to.
  "What was I doing?" is answered by =cerebro today=, the issue tracker
  and Timewarrior, each of which already knows.
- *Safety*: =org-catch-invisible-edits= is =show-and-error=, so you
  cannot silently edit text folded away inside a =:crypt:= subtree (see
  "Encrypted notes") and corrupt the ciphertext.

: make stats

* Digital garden

: make garden

=bin/cerebro-publish-garden=: every note with =#+FILETAGS: :evergreen:=

* Encrypted notes

Tag a heading =:crypt:= and its body is encrypted at rest
(=.emacs.d/lisp/cerebro-crypt.el=, built on Org's own =org-crypt= --
no new Emacs package, just GnuPG from =guix.scm=). Symmetric
(passphrase) encryption by default; set =org-crypt-key= to a real key
ID later if you want asymmetric instead. Decrypt on demand with
=org-decrypt-entry= (=C-c C-x C-d=).

* Spaced repetition

Tag a heading =:drill:= (heading = prompt, body = answer) and =M-x
org-drill= quizzes you over every one, across all of =org-agenda-files=
(=.emacs.d/lisp/cerebro-drill.el=, =emacs-org-drill= from =guix.scm=).
The =f= (flashcard) Org-roam capture template builds the right
structure for you.

* Issues

Personal, non-proprietary issue tracking that doubles as the project's
committed roadmap: Org headings in =issues/issues.org=
(=TODO=/=DOING=/=DONE=/=CANCELLED= + an =:ID:=/=:CREATED:= drawer), no
external service, all versioned in git. Many ways in, all producing the
same plain Org, none locking you into a tool:

- *CLI* (see "Command-line workflow"): =cerebro issue new "title"
  [tags...]=, =cerebro issue list|show|close|start|reopen|report=. The
  full lifecycle from the terminal; =close= logs a =CLOSED= timestamp via
  org-mode itself.
- =C-c c i= (=org-capture=) -- capture one from inside Emacs, with a link
  back to where you were; same heading shape as the CLI.
- =C-c d i / I / c / R= (=cerebro-cli.el=) -- list / new / close / report,
  as thin wrappers over the same CLI.
- =C-c i= -- just open the file and edit it. =C-c a i= -- a focused
  agenda view of every *open* issue (=TODO= and =DOING=), highest
  priority first (=cerebro-agenda.el=); open issues also appear in the
  =C-c a m= morning review.

Closing an issue anywhere -- =cerebro issue close=, =C-c d c=, or =C-c
C-t= to =DONE= -- logs a timestamp into its =:LOGBOOK:= drawer
automatically (=org-log-done=/=org-log-into-drawer=), so the tracker keeps
its own history without any extra step.

* Taskwarrior / Timewarrior

Both are part of the isolated Guix environment (=guix.scm=), along
with =jq= for the hooks below.

- =taskwarrior/hooks/on-add.cerebro=, =on-modify.cerebro=: tasks under
  the =academic= project (or any =academic.*= sub-project) get

** =make compile=: the byte compiler as a gate

: make compile       # the pure modules, warnings are errors
: make compile-all   # ...and report (not enforce) the rest

Twelve thousand lines of Elisp were never once handed to the byte
compiler, which is the one tool that reads all of them and objects. It
catches exactly what no test here can see: a variable name mistyped in a
=setq= (a "free variable" -- the setting silently does nothing), a
function called with the wrong number of arguments, an obsolete Org
function that still works /today/.

It cannot be a gate over everything, and the reason is invariant 4:
outside the pinned environment the soft modules legitimately mention
variables of packages that are not installed -- that /is/ "degrade
feature by feature" -- so promoting their warnings to errors would give
a gate that is red on every machine without Guix. So the gate covers
=cerebro-pure-modules= (declared once, in =cerebro-base.el=, and read by
both this and the test that checks those modules load no Org): a warning
in a module that claims to depend on nothing is a real defect, usually
the dependency creeping back in. It found one on the first run. The
=.elc= files go to a temp directory and are deleted -- Emacs prefers a
=.elc= to its =.el=, so a stale one left in =lisp/= would shadow the
source you are editing.

** The gates, and what they cost

=make test= runs on every commit (=githooks/post-commit=); =make check=
(compile + tests + lint) is what =githooks/pre-push= runs before you
share anything. Both take *seconds* -- and getting there took two
changes, both about the same mistake. =bin/guix-run= does not re-resolve
the pinned channel when you are already inside the environment; and the
steps that are pure Elisp (the tests, the compile gate, the linter) no
longer go through it at all, because they load nothing from =guix.scm=.
Outside the environment =make check= was *3 m 37 s*, of which about ten
seconds was work: one =guix time-machine= for the tests and another for
the lint. It is now *26 s*. A gate that slow is a gate you learn to skip
with =--no-verify=, which is worse than not having one.
=CEREBRO_GUIX_FORCE=1= takes the pinned path deliberately -- the check
to run after editing =guix.scm=.

=make export-matrix= is the heavy gate and runs on no hook at all: every
named profile compiled against =notes/README.org=, plus all four
documents of a real course end to end (the =#+INCLUDE= machinery is
load-bearing now). Run it after
touching =latex/=, the export profiles or the course generator --
=make ci= is =check= plus that. It materialises the pinned environment
*once* for the whole matrix, by re-entering =make= inside it (guix-run is
a no-op once =GUIX_ENVIRONMENT= is set, so each compile then runs
directly) -- it used to pay for one channel resolution per compile. It
stays serial, and =make -j= cannot change that: every profile of one
source writes the same =.build/<name>.tex=, because the build is named
after the /source/, not the profile.

* Making a note: one keystroke, one result

The unit of this archive is /one result per note/ -- a definition, a
theorem, a construction. That only works if making one costs nothing: the
moment it involves choosing a file name, a directory and a template, the
idea gets appended to whatever buffer is open and the graph stops
growing. So =cerebro-math.el= makes it a keystroke.

| Key       | What                                                     |
|-----------+----------------------------------------------------------|
| =C-c m t= | a theorem note -- you are typing inside the block already |
| =C-c m d= | a definition   (=l= lemma, =p= proposition, =c= corollary, =x= example, =r= remark) |
| =C-c m n= | ask which kind                                            |
| =C-c m e= | /extract/: the selected statement becomes its own note, with a link left behind |
| =C-c m f= | open a note from =notes/math/= -- /by title/, since the file names are digests |

What it fills in without asking, because each of these is something that
fails silently when forgotten:

- a *file name you never see, and could not have chosen*: the digest of
  the note's own metadata (see below). You are never asked what to call
  the file, because the file has no name to give -- an untitled fragment
  and a finished theorem are named the same way.
- a file-level *=:ID:=*, so it is an Org-roam node with backlinks the
  moment it exists (and =org-id-add-location= registers it immediately,
  so you can link to it from the very next keystroke).
- =:seed:= maturity and an empty =#+MSC:= -- born classified, exactly like
  =cerebro note new= and the capture templates.
- the right *block* (=#+begin_theorem=, ...) with a =#+NAME:= directly
  above it, carrying the prefix the results layer reads (=thm-=, =def-=,
  =lem-=, ...). The note is part of the logical-dependency graph (=C-c r
  i=) from the start, instead of after you remember to name it.

=C-c m e= is the one that grows a Zettelkasten out of prose you already
wrote: select a statement buried in a long note, and it becomes a node of
its own -- citable, dependable-on, with backlinks -- while the place it
came from keeps an =id:= link. Nothing is lost from either side.

The generated text is built by pure functions and unit-tested against the
same conventions =bin/notes-lint.el= enforces (=#+NAME= touching its
block, a real theorem environment, no naked =$=), so what these commands
write cannot drift from what the linter accepts.

** The file name is the metadata

A note in =notes/math/= is called =dc371dcdc869.org=. That is the
SHA-256 digest of its own front matter -- =:ID:=, =#+TITLE=, =#+DATE=,
=#+FILETAGS=, =#+MSC=, in that order, one field per line -- truncated to
twelve hex characters, recorded in the file as =#+HASH:=, and recomputed
every time the note is saved (=cerebro-hash.el=). Change the title, the
tags or the classification and *the file renames itself*; rewrite a
proof and it does not, because the proof is not part of what the note
/is/.

Why give up a readable name:

- *A file name is a second title, and a second title goes stale.*
  =20260806140000-supremum.org= went on saying "supremum" long after the
  note had been retitled -- and renaming a file is work nobody does.
  Nothing here resolves a note by path (links are =id:= links), so the
  name was pure decay with no compensating use.
- *A digest is checkable, and a name is not.* =cerebro lint= recomputes
  it and reports any file whose name no longer follows from its
  contents -- drift introduced by another editor, a =git checkout=, or a
  hand-written file. =cerebro note rehash= re-derives every name in one
  idempotent pass; that is the repair, and it is also the migration.
- *It forces the metadata to be worth reading*, since it is now the only
  description of the note outside its own prose. Hence the strictly
  ordered, one-per-line front matter: data a three-line shell script can
  parse, not prose a parser has to guess at.

The cost, stated plainly: =ls notes/math/= is unreadable. That is what
=C-c m f=, =cerebro note find QUERY=, =cerebro note list= and the
org-roam search are for -- every one of which reads the title out of the
file, which is where a title belongs.

Two programs compute this digest: =cerebro-hash.el= and, so the CLI needs
no Emacs, =bin/cerebro-note= in POSIX sh. If they ever disagreed, each
would rename every note the other had just named -- so both are pinned to
one literal constant, asserted by the ERT suite /and/ by the shell test
suite.

* Reading the PDF inside Emacs

The export pipeline produces a real typeset document, and looking at it
used to mean leaving the editor. =cerebro-pdf.el= closes that loop:

| Key       | What                                                        |
|-----------+-------------------------------------------------------------|
| =C-c e e= | compile this note and show the PDF beside it (=C-u=: pick a profile) |
| =C-c e r= | compile *only the result at point*, through the =single= profile |
| =C-c e v= | show the PDF that is already there                           |
| =C-c e o= | open a course; =C-c e c= / =a= / =p= build and show its documents |
| =C-c e d= | the PDF in the editor's colours <-> as it will be printed    |
| =C-c e s= | why is there no PDF? (viewer, helper binary, staleness)      |

- The compile is *asynchronous*, in a compilation buffer. A real latexmk
  run takes seconds and =org-latex-export-to-pdf= is synchronous -- an
  editor that freezes on export is one you stop exporting from. That
  buffer is also where a LaTeX error appears, which matters here because
  exports are strict (=-halt-on-error=).
- It shells out to =bin/org-export-latex.el=, the same batch entry point
  =make export= uses: one implementation of "compile a note", not two.
- The PDF opens in a right-hand side window with =auto-revert-mode=, so
  re-exporting refreshes the page you are reading instead of opening a
  second buffer. Note left, paper right, both live.
- =C-c e r= is the fast loop while writing a proof: the =single= profile
  keeps one =#+NAME='d block plus its proof and nothing else, and the
  name is read from the buffer, so checking one theorem's typesetting
  costs no typing and no full-note compile.
- The page is rendered in the *editor's own colours* by default: a white
  page in a dark frame is the brightest thing on the screen, and it sits
  right next to the note you are reading. pdf-tools does this through
  the renderer's colour filter (the real page recoloured, not an image
  inverted), and it follows =C-c u t= -- the mode itself only refreshes
  on save, so a theme switch would otherwise leave every open PDF in the
  palette you just left. =C-c e d= shows the printed page when that is
  what you actually want to check.
- The viewer is =pdf-tools= when the environment has it, and Emacs' own
  =doc-view= (through poppler's =pdftoppm=) otherwise. Both are checked
  at *runtime*: pdf-tools renders through a helper binary, and a profile
  that has the Elisp without the binary must fall back to the built-in
  viewer rather than fail on the first page.

* Writing code (and notes) with help

=cerebro-code.el=. This repo is a second brain *and* about three thousand
lines of Elisp and POSIX sh that keep it working, edited in the same
session. Each feature here is layered on a mechanism already inside
Emacs, not on a framework:

- *Diagnostics while you type* (=flymake=, built in). Elisp is checked by
  the byte-compiler Emacs already carries, shell by =shellcheck= -- and,
  the one that matters most here, *notes are checked by this repo's own
  linter*: a naked =$=, a dangling =#+DEPENDS:=, an undeclared tag get
  underlined in the note on save, instead of surfacing in a git hook
  minutes later. The backend runs =bin/notes-lint.el=, the same program
  the pre-push gate runs, so what you see while writing is what will
  block the push.
- *Templates* (=tempel=), expanded through the same completion popup as
  everything else -- no second UI to learn. The templates are data in
  =.emacs.d/templates=, and the Org ones are this project's conventions
  made into muscle memory: =thm= expands to a =#+NAME:= touching its
  =#+begin_theorem= with a proof block after it; =m= / =dm= to =\(...\)=
  and =\[...\]=, never =$=.
- *Format on save* (=apheleia=), in a subprocess so point and undo
  survive -- for *code*. Prose is never reflowed: a note is a
  mathematical text and its line breaks are the author's.
- *Structure you can see*: indentation bars in code (never in prose,
  where Org's own indentation is the structure), and a *breadcrumb*
  header line -- in a note the outline path of the heading you are
  under, in code the enclosing definition.
- *Tree-sitter* where a grammar exists. Emacs 30 has the engine built in
  and guix.scm ships the bash grammar. Worth stating plainly: neither Org
  nor Emacs Lisp has an upstream tree-sitter grammar, so this applies to
  =bin/*.sh= and to nothing else in this repo -- it is wired from a table
  and says so rather than pretending to be everywhere.

One rule holds all of it together: none of this runs in the notes that
the agenda, the dashboard or org-roam open *in the background* to read
(=cerebro-code-interactive-buffer-p=). Dozens of files are opened and
killed on every dashboard refresh; starting a linter process and a
preview timer in each one is both slow and wrong -- and it was visible,
as a "Cache must be active" error every time the start page refreshed.

* The look: theme, typography, status line, focus

The brief, stated once because everything below follows from it:
/minimal chrome, maximal legibility, and a screen that resembles the PDF
the same file compiles to./ Five modules, each one table of data plus a
few functions, each degrading outside the pinned environment.

| Key           | What                                                       |
|---------------+------------------------------------------------------------|
| =C-c u t=     | dark <-> light (=modus-vivendi= / =modus-operandi=)         |
| =C-c u + / -= | body size, frame-wide -- headings and formulas follow       |

| =C-c u f=     | focus mode: a centred column of ~92 characters              |
| =C-c u m=     | the status line, off/on                                     |

| =C-c u s=     | cycle: source -> write -> study                             |

| =C-c u o=     | straight to /source/ (the file as it is)                    |
| =C-c u S=     | pick a mode by name                                         |
| =C-c u i=     | compile the =#+begin_src latex= figures inline              |

| =C-c u R=     | rebuild the precompiled preview format (after a TeX bump)   |
| =C-c u P=     | why is nothing rendering? how big? how fast?                |
| =C-c u c=     | pick a look by name (dark, light, pastel, pastel-light)     |
| =C-c u b=     | the breadcrumb header line, off/on                          |
| =C-c j=       | jump to any character you can see (=avy=)                   |

- *Six looks in three pairs, two of them free* (=cerebro-theme.el=).
  =hermes= / =hermes-light= (ef-themes) are the default: iron gall ink by
  candlelight, and the sepia parchment side of the same register -- meant
  to sit under the engraving on the start page rather than fight it.
  =pastel= / =pastel-light= are the cooler, undated alternative; =dark= /
  =light= (modus) are the fallback that needs no package at all, and what
  you get if ef-themes is ever missing -- refusing to start because a
  /colour scheme/ is absent would be the silliest way to lose an editor.
  =C-c u t= switches between the light and dark version of the look you
  chose; =C-c u c= picks a different look.

  Both theme families are configured on every apply, which they were not:
  every option in the setup was named =modus-themes-...=, so under the
  ef-based variants -- four of the six -- it did nothing. They had no
  heading scale and, worse, no =mixed-fonts=, the setting that keeps Org
  tables and aligned mathematics monospaced when headings are
  proportional.
- *Icons that are text* (=nerd-icons=). A Nerd Font puts a few thousand
  glyphs into a normal monospace font, so icons scale with the text,
  render in a terminal frame and need no image support. They appear in
  the minibuffer, the completion popup, the file tree and the start page
  -- and only when a Nerd Font is actually installed
  (=cerebro-theme-nerd-icons-p=), because a missing glyph is a visible
  box.
- *The start page* (=cerebro-dashboard.el=, =C-c h=) is titled
  =κέρεβρο= -- the name in Greek, in blue, and nothing else. The sentence
  that used to sit under the banner explained the archive to someone who
  is not the person opening it, every morning.

  Its sections are marked with the classical planetary signs, each the
  one this tradition already attaches to what the section is about, so
  the page reads by shape before it reads by word: ♄ Saturn for the open
  issues (what binds), ♂ Mars for what still owes a proof, ☽ Luna for
  what has just changed, ♃ Jupiter for the seeds that should be growing
  and are not, ☉ Sol for what you can do. Every sign is checked against
  the font in use and falls back to a plain-ASCII marker -- a row of
  empty boxes is worse than a row of dashes.

  Under ☉ is the *key panel*: five rows, one per thing one does here --
  open the day, write mathematics, read it back, find something, make a
  document -- each with the three keys that do it. Those keys are data,
  and a test checks every one of them is really bound, because a start
  page that advertises a key nobody bound is worse than one that
  advertises nothing: it is checked once, believed, and then quietly
  wrong.
- *Motion on the start page* is Emacs': =n= / =p= and the arrows.
  emacs-dashboard also binds =j= / =k= for it, vim-style, and those are
  switched off (=cerebro-dashboard-disable-vim-motion=). Not only as a
  preference: the *section shortcuts* live in the same keymap, so a
  section whose shortcut was =k= and =k= = previous-line were one key,
  and which one you got depended on load order. The shortcuts are now off
  every motion letter -- =w= work, =i= issues, =r= recent, =u= unproved,
  =s= seeds.
- *The start page's art* is =.emacs.d/hermes.jpg=: the engraving of
  Hermes Trismegistus with an armillary sphere, pointing from the
  instrument in his hand to the sun and moon it measures. Point
  =cerebro-dashboard-banner= at any image of your own to replace it --
  the format is read from the file, so PNG or JPEG both work, and on a
  terminal frame (or an Emacs that cannot decode that type) the start
  page falls back to a text logo. =bin/cerebro-banner= remains: it draws
  a ringed planet in the theme's pastel range with ImageMagick, offline,
  as =banner.png=, for a generated banner rather than a supplied one.
- *Theme and typography* (=cerebro-theme.el=). The palette is
  =modus-vivendi=/=modus-operandi= -- /built into Emacs/ since 28, so the
  most visible half of the config owes nothing to a package that can go
  unmaintained, and they are the only widely used themes designed to meet
  WCAG AAA contrast. What this module adds is data: a font *preference
  list* per role (mono / proportional / serif) resolved to the first
  family actually installed, so a fresh clone on a new machine never
  lands on a missing font; a heading scale (1.30/1.20/1.10/1.05 --
  shallow on purpose: a section title three times the body size is
  decoration, not structure); and a short list of palette overrides that
  only /quieten/ chrome (a flat mode line, an untinted fringe, dimmed
  comments). One number, =cerebro-theme-font-size=, drives everything
  that scales, and =cerebro-theme-after-apply-hook= is the seam anything
  colour- or size-dependent hangs off -- including the *cursor*, which is
  a face and is therefore replaced by every =load-theme=. It is a
  three-pixel bar painted in the *body text* colour: one pixel (the
  default of =bar=) with blinking off and =global-hl-line-mode= under it
  is a cursor you cannot find, and a colour taken from the theme's own
  accent is chosen to look right rather than to be seen. The text colour
  contrasts with the background by definition and with the current-line
  highlight because themes are built that way, so the cursor is visible
  by construction in every variant, including ones added later
  (=cerebro-theme-cursor-type=, =cerebro-theme-cursor-follows-text=) -- which is how previews stay
  correct across a theme switch without the theme module knowing they
  exist. =spacious-padding= (guix.scm) puts real space between the text
  and the frame; without it the fallback is =internal-border-width= plus
  fringes, the same idea with built-ins.
- *Status line* (=cerebro-modeline.el=). Built from *segments*: small
  pure functions listed in two data variables (left group, right group).
  Two of them are things only this repository can say, and are the reason
  the line is worth reading: =thm-mean-value= -- the =#+NAME='d result
  point is *inside*, which is the question with no other cheap answer
  while reading a long note, since a proof three screens below its
  statement looks exactly like a proof of whatever is above it -- and the
  note's rung on the maturity ladder (=seed= drawn as an alert), because
  a state nobody can see is a state nobody reconsiders, which is how an
  archive fills with notes that were seeds two years ago. Both are
  *bounded* searches (=cerebro-modeline-search-limit=): a segment runs on
  every redisplay, ~100 times a second while scrolling, and an unbounded
  backward search in a long note is the exact shape of the bug that made
  scrolling unusable before. Measured at 17 and 22 microseconds.

  The rest is what changes here -- unsaved state, the note's
  place in the notes tree (twenty theorems named after twenty theorems
  live in different courses), a running =org-clock= (it is costing you
  time, and =cerebro-time.el= mirrors it into Timewarrior), the git
  branch, and =host= when this Emacs is /not/ the pinned one. No icons,
  no package: it renders identically in a terminal. An unfocused window
  shows only what it is, since the clock and the branch are global facts.
- *Org presentation* (=cerebro-appearance.el=). =org-modern= draws
  headings, bullets, blocks, tags and timestamps as shapes rather than
  markup; =org-appear= brings the emphasis markers back when point walks
  into a word (the papercut =org-hide-emphasis-markers= otherwise
  creates). *Mathematics is not redrawn*: =org-pretty-entities= is off,
  so =\in=, =\pi= and =x_{1}= stay the linear text the file contains.
  Turned on it substitutes a glyph for the entities Org happens to know
  and leaves =\eps=, =\abs{x}= and every =cerebro-macros.sty= command as
  source next to them -- a formula drawn half-way, hiding precisely what
  you read the buffer to check. The honest preview is the one that
  compiles (=cerebro-preview.el=, below). Prose soft-wraps, because the
  note conventions require a display equation to sit on one physical
  line. =hl-todo=
  highlights =TODO=/=FIXME= /and =CEREBRO-ISSUE:=/ -- the marker
  =cerebro issue scan= imports into the committed tracker, until now
  invisible in the comment you left it in. Nothing here changes a byte of
  a note: every effect is display only.
- *Formulas in the buffer* (=cerebro-preview.el=). Org renders LaTeX
  fragments in place, and this points that machinery at the /same source
  of truth the exporter uses/: =latex/cerebro-macros.sty=, found through
  the same =TEXINPUTS=. So =\norm{x}=, =tikz-cd= diagrams and pgfplots
  figures preview with the meaning they will have in the PDF -- and a
  fragment that fails to preview is a fragment that will fail to compile.
  The renderer is chosen from what is installed (=dvisvgm= for vector
  output, then =dvipng=, then nothing) instead of failing per fragment;
  the delimiters are the ones the linter allows (never =$...$=); the
  generated images are cached under =.emacs.d/var/=, not scattered
  through =notes/= as =ltximg/= directories. =org-fragtog= makes the
  fragment at point turn back into source while you edit it. A rendered
  formula is a /bitmap/ carrying the colour and size it was drawn at, so
  switching theme or font size drops the ones on screen
  (=cerebro-preview-on-theme-change=) rather than leaving a page of
  formulas in the palette you just left. Two things it now gets right
  that it did not (both in "Formulas, at the size of the prose" above):
  the *size* -- the magnification the converter receives is provably
  independent of the display, which is what stopped every formula being
  ~3.7x too large on a HiDPI screen -- and the *speed*: the preamble is
  compiled into a LaTeX format file once, and a fragment renders in
  202 ms instead of 663 ms.
- *Moving through the archive* (=cerebro-nav.el=, =C-c r=). The results
  graph existed only as *reports*: =C-c r i= told you where every named
  result lived, and you then navigated there by hand. The same data, as
  movement: =C-c r j= jumps to any result in the archive by name (which
  is also the answer to "did I already state that, and what did I call
  it?" -- the question that otherwise produces a second theorem with a
  second name); =C-c r n= / =C-c r p= walk the named results of the note
  you are reading; =C-c r u= walks the ones that still owe a proof, note
  by note, because a work list you can only read is a work list you do
  not do; =C-c r b= shows what links here. And =C-c r D= writes a
  =#+DEPENDS:= line by *completing over the names that exist* -- typing
  them from memory is how a dangling dependency gets written.

  It is a separate module from =cerebro-results.el= on purpose: that one
  is pure, requires no Org, and a test asserts it never loads it, which
  is what keeps =cerebro results check= a 60 ms shell command.
  Navigation is nothing but buffers, windows and point.
- *The documentation, from inside the editor* (=cerebro-help.el=,
  =C-c H=). This repository documents itself at length and none of it
  was reachable without leaving Emacs. =C-c H h= the manual, =C-c H c=
  the note conventions, =C-c H b= the operational brief, =C-c H d= any
  of them by name. Two more are *derived* rather than written, which is
  the point: =C-c H k= lists every cerebro key grouped by prefix, read
  from the live keymap, so a binding that moved is reported where it
  moved to; =C-c H v= lists every cerebro setting *with its current
  value* and opens =describe-variable= on the one you pick, generated by
  =apropos= so a defcustom added later appears without being registered
  anywhere. =C-c H m= is the module map, read from each module's own
  header line. A reference maintained by hand goes stale the first time
  something moves, silently -- and documentation that is quietly wrong
  is worse than documentation that is missing.
- *What you are doing to the note* (=cerebro-study.el=, =C-c u s=). A
  note is read and written in the same buffer, and those want opposite
  things. Three named modes, one table of data:

  | mode     | rendered | markup   | follows point | column  | numbers |
  |----------+----------+----------+---------------+---------+---------|
  | =source= | no       | visible  | no            | full    | yes     |
  | =write=  | yes      | hidden   | *yes*         | full    | no      |
  | =study=  | yes      | hidden   | no            | centred | no      |

  =source= is the one to reach for when a preview disagrees with the PDF
  and you need to see the bytes; =write= is the working mode, where the
  formula at point turns back into source as you arrive at it; =study=
  is reading. The mode is shown in the status line -- =source= in the
  alert face, because a mode that renders nothing would otherwise look
  like previews that had failed.

  The interesting column is *follows point*, and it is why this exists
  at all rather than being a preference. =org-appear= and =org-fragtog=
  both watch point from =post-command-hook=, and each asks
  =org-element-context= where point is -- ~4 ms per call on a note of
  average size. A trackpad under =pixel-scroll-precision-mode= issues
  around a hundred commands a second, and point moves in *none* of them,
  so roughly 800 ms of every second of scrolling went to re-answering an
  unchanged question. That was the scrolling lag, and it was not a bug
  in either package: they do what a writing mode should do. It was a bug
  in having no other mode, and in switching them on from =org-mode-hook=
  for every buffer. Now they belong to =write=, and reading a note runs
  no timers at all.
- *Focus mode* (=cerebro-focus.el=, =C-c u f=). A centred column of
  =cerebro-focus-width= characters (the measure problem: a line of
  mathematical prose is comfortable at 70-90, a maximised frame is 200+),
  with the editing chrome taken away and prose optionally proportional
  while tables, code and inline LaTeX stay monospaced. A toggle, not a
  default -- and it restores every single thing it changed.

* The workspace: start page, tree, completion, git

A database you keep for a lifetime is only as good as your ability to
/reach/ something in it. Four small modules make the editor a workspace
for the notes rather than a bare text editor pointed at them:

| Key       | What                                                        |
|-----------+-------------------------------------------------------------|
| =C-c h=   | the start page (=cerebro-dashboard.el=)                      |
| =C-c f n= | a note by title (=m= math, =j= conjecture, =c= course, =r= result) |
| =C-c s=   | grep the text of every note, live                            |
| =C-c g=   | =magit-status= (=C-x g= works too)                           |
| =C-c w u/r= | undo/redo a window layout (=winner-mode=)                  |
| =C-c G s= | what environment am I running in? (see below)                |

- *Start page* (=cerebro-dashboard.el=). Opening the brain lands on a
  page that answers the three questions you actually have when you sit
  down: what is open (the most urgent issues, ranked exactly as =C-c a
  i= ranks them), what you were writing (the notes whose /file mtime/ is
  newest -- so a note created by the shell CLI or pulled from git counts,
  not just what this Emacs visited), and what is scheduled (the agenda).
  Four sections, in the order the questions arrive: what is open, what
  the archive still owes a proof, what you were writing, and which seeds
  have sat longest. A one-line census -- notes, named results, open
  issues -- sits under the banner, and grows an environment summary *only* when this Emacs is
  not the pinned one, which is exactly when you need to see it. The
  agenda is deliberately not a section: rendering it means scanning every
  agenda file on every refresh, and it is one keystroke away
  (=C-c a m=, or the [Morning review] button). The data functions are pure Elisp over the plain-text
  sources and unit-tested; =emacs-dashboard= only draws them, so there is
  no cached state that can go stale, and without that package the same
  information still renders in a plain buffer.
- *The archive is writable; the machinery is not*
  (=cerebro-isolation.el=). The environment was isolated outside Emacs --
  guix.scm pins everything, nothing is fetched at runtime -- and not at
  all inside it: the same editor that writes a theorem could rewrite
  =cerebro-latex.el=, the makefile or =guix.scm=, and the difference
  between those two acts was a directory nobody checked. Now
  =notes/=, =issues/= and =bib/= are writable and everything else in the
  repository opens read-only. Reading the config still works -- that is
  what =C-c H= is for; typing into it does not.

  Stated plainly, because overstating it would be worse than not having
  it: *this is a guard rail, not a lock*. =buffer-read-only= is one
  =C-x C-q= away on purpose, and =C-c H u= is the sanctioned version of
  that keystroke, which reports what it did. The point is not that
  editing the configuration is forbidden; it is that it should be a
  deliberate act rather than something that happens because a buffer was
  open and the cursor was in it. A second brain that made its own
  configuration unreachable would be a second brain you cannot fix.
  =C-c H i= says what the policy currently is.
- *There is no file tree*, and files are reached by *kind*
  (=cerebro-find.el=, =C-c f=). A tree answers "what is in this
  directory?", which is not a question this archive has: the questions
  are "which note was that", "which course", "which conjecture" -- about
  kinds of writing, and the archive already knows the kinds. =C-c f n=
  any note · =C-c f m= a math note · =C-c f j= a conjecture · =C-c f c= a
  course · =C-c f r= a named result · =C-c f i= issues · =C-c f b= the
  bibliography. Everything completes over *titles*, never file names --
  forced rather than chosen, since a note in =notes/math/= is called
  =a3f19c04b2e7.org= (=cerebro-hash.el=), so file-name completion would
  be completion over noise. Two notes sharing a title are disambiguated
  by directory rather than one shadowing the other: a note you cannot
  find is a note you conclude you never wrote. The sidebar this replaced
  (=dired-sidebar= + =dired-hacks=) is gone from the config *and* from
  =guix.scm=; =C-x d= is still dired.

- *Completion* (=cerebro-complete.el=). =vertico= (candidates listed
  vertically), =orderless= (=heine borel= matches "Borel--Heine covering
  theorem"), =marginalia= (annotations), =consult= (live search: =M-s l=
  line, =M-s g= grep, =M-g o= outline, =C-x b= buffers). Each improves
  the /built-in/ completion machinery instead of replacing it: drop any
  one and completion falls back to vanilla Emacs. Note the three search
  surfaces are deliberately different questions -- =C-c s= searches note
  /text/, =C-c n f= searches by title through the org-roam graph, =C-c v
  s= searches Org /metadata/ through org-ql. =C-c s= goes through
  *ripgrep* (guix.scm) when it is there, then consult+grep, then the
  built-in =rgrep=: consult re-runs the search on every keystroke, so how
  fast the archive can be scanned is how interactive "where did I write
  that" feels. Fuzzy in the sense that matters: type =borel heine cover=
  and the words match in any order, because consult sends the first token
  to ripgrep and =orderless= filters the rest. The same idea applies
  /inside/ the buffer: =corfu= shows completion-at-point candidates in a
  small popup instead of a window behind your text, and =cape= is what
  there is to complete -- words already written in the note (a note
  repeats "quasi-isomorphism" and "Lebesgue-measurable"; completing them
  from your own text is both faster and a spelling check), file paths,
  Elisp symbols. =TAB= indents or completes in code buffers; Org is
  untouched, since it binds =TAB= to =org-cycle=.
- *Navigation feedback* (=cerebro-ui.el=). =pulsar= briefly lights the
  line you land on after a jump or a window switch -- the expensive
  moment is not the jump, it is hunting for point afterwards. =avy=
  (=C-c j=) is the third way to move, next to searching the text and
  completing a name: type a couple of characters you can /see/.
- *Git* (=cerebro-vc.el=). The second brain is a git repo whose gates are
  git hooks, so committing is a daily in-editor operation. Magit saves
  note buffers before staging (a half-typed note still only in a buffer
  is invisible to =git add=) and shows the hooks' output, so a failing
  =make test= in =post-commit= is something you see.
- Prefixes are discoverable: =which-key= (Emacs core since 30) lists what
  can follow =C-c n/v/q/r/d/G/w/u=, with a label per prefix.

Every one of these packages is pulled through
=cerebro-guix-soft-require=, so *none of them is load-bearing*: outside
the pinned environment the modules still load and simply degrade feature
by feature (stock completion, no sidebar, a plain-text start page) --
see "Robust startup" below.

* The environment, from inside Emacs

=.emacs.d/lisp/cerebro-guix.el= makes the pin observable from the editor
it produced. Previously nothing inside Emacs told you whether the session
came out of the pinned profile or off the host's =PATH= -- and the two
differ in exactly the ways that matter (org-roam, org-ql, org-drill,
aspell, latexmk, the workspace packages above). "Why is =C-c n f=
undefined today?" should not require reading three shell scripts.

: C-c G s   status: profile, channel pin, and which guix.scm packages loaded
: C-c G m   open guix.scm            C-c G c   open guix/channels.scm
: C-c G b   materialise the environment (bin/guix-run, in a compile buffer)
: C-c G r   run one command inside it   C-c G R   re-pin the channels

The same report is scriptable -- =cerebro env= (or =make env=), which
runs it /through/ =bin/guix-run= so that what it prints is what the
editor gets, not what the calling shell happens to have. It complements
=cerebro doctor=: doctor checks which tools exist on the host, =env=
checks which Emacs packages the pinned profile actually hands the config,
and at which channel commit.

Two details worth knowing. The "am I isolated?" test is =GUIX_ENVIRONMENT=
being set, which =guix shell= sets to the profile it built -- one honest,
zero-cost signal, no guessing from paths. And the list of packages the
report iterates is a single defconst
(=cerebro-guix-optional-packages=): adding a package to =guix.scm= means
adding one datum there, and it shows up in the status report, in the
dashboard census and in the startup warning at once.

* Backups: a policy, not a script

: cerebro backup status        what is configured, and when it last worked
: cerebro backup               run every enabled target
: C-c B s / C-c B b            the same two, from the editor

Git history is not a backup while the only clone is on this machine, and
this repository is meant to hold decades of work. What it cannot do is
*choose* where your copy goes -- that is a decision about your life, not
about the software -- so a backup here is a **target**: a name, a shell
command, and whether it is switched on. Three cover almost every
arrangement:

| Target    | What it does                                              |
|-----------+-----------------------------------------------------------|
| =git=     | push every branch and tag to a remote you control          |
| =mirror=  | =rsync= the working tree to a disk, a server or a share    |
| =archive= | one =gpg=-encrypted tarball per run, for cold storage      |

Nothing is enabled out of the box, and an unconfigured target builds *no
command at all* rather than half of one -- =rsync -a ./= with an empty
destination is not a backup, it is a mistake with a progress bar. Set
=:enabled= and =:value= (the remote, path or directory) in
=cerebro-backup-targets=; your server names belong in the gitignored
custom file cerebro-session.el already keeps, not in this repository.

Each successful run appends a line to =.emacs.d/var/backup-log=, plain
text on purpose: "when did this last work?" has to be answerable on a
machine where Emacs no longer starts. =bin/cerebro-backup= is cron-able
and exits non-zero when a target fails.

* Robust startup & housekeeping

A second brain "meant to last" has to survive being opened in an
imperfect environment and must not litter its own plain-text repo.
Both are handled with Emacs core only (no new Guix package):

- *Graceful degradation* (=init.el=): the modules split into /core/
  (pure Elisp on Emacs core -- Org, LaTeX export, the taxonomy) and
  /optional/ (the ones pulling a guix-only package: =org-roam=,
  =org-ql=, =org-drill=). Core is required loudly -- a failure there is
  a real bug. The optional ones load best-effort: started *outside* the
  guix environment (where those packages are absent) Emacs no longer
  aborts init on the first missing =require= and drops you in a broken
  editor -- it loads the pure half, and reports once which modules were
  skipped and how to get them (=make shell=). This is not a network
  fallback (nothing is fetched); only a promise that one absent package
  can't brick the editor.
- *Degrading feature by feature, not module by module* (the workspace
  modules =cerebro-{complete,ui,vc,dashboard}.el=): these each configure
  several independent packages, so an all-or-nothing =require= would
  throw away completion because the file tree is missing. They pull every
  package through =cerebro-guix-soft-require= instead, which records an
  absent one as a datum rather than raising -- so the module always
  loads, configures what it got, and =C-c G s= / =cerebro env= lists
  exactly what is missing and why (see "The environment, from inside
  Emacs"). The rule for new code: anything from =guix.scm= that is not
  strictly required goes through that function.
- *The whole notes tree is one corpus* (=cerebro-note-directories= /
  =cerebro-note-files= in =cerebro-org.el=): =org-agenda-files= expands
  a /directory/ entry only to the =.org= files directly inside it -- it
  does *not* recurse -- so nested notes (=notes/courses/*/=,
  =notes/conjectures/=) used to be invisible to the agenda, the morning
  review, and =org-drill=. The agenda is now built from every
  subdirectory of =notes/=, and the org-ql surface (=cerebro-ql.el=)
  reuses the same "where the notes are" helper, so the two query
  surfaces provably scan the same files.
- *A clean git tree* (=cerebro-session.el=): backups (=foo~=),
  auto-saves (=#foo#=) and lock files (=.#foo=) are redirected out of
  =notes/= into a gitignored =.emacs.d/var/=; Customize writes to
  =var/custom.el= instead of appending machine-written
  =custom-set-variables= into the *tracked* =init.el=; and a little
  harmless session state (recent files, minibuffer history, per-file
  cursor position, all built-in) persists there too.

** LaTeX certification

Every profile is compiled end to end as part of =make export-matrix=:
=syllabus=, =lecture=, =slides=, =handbook= and =single= against
=notes/README.org=, then all four documents of =analysis-A= from its own
=course.org= -- each producing a PDF with no error. The rendered pages
were also *looked at*, which is the only way to check a claim like
"minimal" or "nothing overlaps".

*Strict compilation.* =org-latex-pdf-process= runs =latexmk
-halt-on-error= (=cerebro-latex.el=): a real LaTeX error now *fails* the
export instead of Org's default =nonstopmode=, under which TeX would
"insert a =$= and proceed", shipping a malformed PDF the matrix wrongly
counted as success. Running the whole matrix under this strict process
surfaced -- and fixed -- real latent bugs that had been hiding, among
them a =\newtheorem{solution}= clash under some beamer/TeX Live
versions; cerebro-beamer.cls now declares each environment defensively
(=\@ifundefined=), so it only defines what beamer lacks.

One more was found the same way and is worth recording, because it is the
exact failure mode this repository keeps warning about: =#+begin_example=
is *not* a special block -- Org parses it as its own =example-block=
element -- so the block filters, which only ever looked at special
blocks, never saw one. The =lecture= profile said it dropped examples and
silently kept every single one. Both filters now ask Org what the element
is (=cerebro-latex--block-type=), and a test pins it.

** Rigor and logical controls

The notes are held to a purely-parsable, world-class standard, enforced
mechanically so a slip fails loudly rather than silently:

- *Inline math is =\(...\)=, display =\[...\]= -- never bare =$...$=.*
  Bare =$= is genuinely fragile in Org (=$x$--$y$= silently degrades the
  first fragment to a literal dollar that then fails to compile); the
  linter rejects any naked =$= outside a src/example/export/comment block.
- *The results dependency graph* (=cerebro-results.el=, "Results layer"
  above): =#+DEPENDS= makes the logical structure -- theorem rests on
  lemma rests on definition -- explicit, queryable, and checked. A
  dangling dependency, a dependency cycle, and a duplicate result name are
  hard linter errors; an unnamed referenceable result and a misplaced
  proof are advisory nudges.
- *A note's file name is derived data* (=cerebro-hash.el=): in
  =notes/math/= it is the SHA-256 digest of the note's own front matter,
  recomputed on save. A name that means something is a second title, and
  a second title goes stale; a digest can only be *wrong*, and the linter
  recomputes it and says so. =cerebro note rehash= repairs a directory.
- =notes/README.org= is the exemplar: fully =#+NAME='d, a worked
  =#+DEPENDS=, all inline math in =\(...\)=, and it passes =make lint=
  with zero advisories while exercising every export profile.
